# macOS notes

Short, practical notes for running this project on macOS. The deeper evidence — what macOS 15
actually ships for Bluetooth audio, why Control Center only shows a noise-control tile for
Apple/Beats devices, and why a kext/DriverKit codec takeover is not available on Apple Silicon —
is in [macos-integration-limits.md](macos-integration-limits.md). That file is generated by the
analysis task (macOS 15.7.2 build 24G325, Apple Silicon, controller `BCM_4388C2`) and is the
source of truth for the claims below; this page does not repeat its commands and quotes.

## The one-time Bluetooth permission prompt

The first CoreBluetooth call triggers macOS's Bluetooth permission prompt for the process that
makes it — the terminal when you run `edifierctl` or `edifier-mcp` from a shell, or the app bundle
when the menu bar app runs as one. CoreBluetooth blocks until the prompt is answered, so
`edifier-link` caps adapter acquisition at 20 s and reports:

> CoreBluetooth did not answer within 20s — if macOS is showing a Bluetooth permission prompt,
> allow it for this app, then retry

Grant it in **System Settings → Privacy & Security → Bluetooth**. No root and no SIP change is
needed: this project controls the headset purely through CoreBluetooth (BLE GATT) in userspace.
A denied prompt is not a bug in the tooling; retry once the toggle is on.

## The control link is not the audio link

The Mac talks to the headset over its BLE control service, which is separate from the classic
Bluetooth audio link. The headset can be playing from a phone while this Mac still controls ANC,
EQ and the rest, and the reverse holds too: `connect-audio` (`edifier_connect_audio`) asks
IOBluetooth to open the paired device's classic connection, the same thing `blueutil` does, to pull
audio back to this Mac. `edifier_disconnect` only closes the BLE control link; it does not touch
audio.

## What macOS cannot do

- **LDAC.** There is no LDAC A2DP encoder, so `ldac 48k` / `49 01` (and `96k` / `49 02`) leaves the
  headset expecting a codec this Mac cannot feed and audio stops until the mode is set back to
  `off`. The control link keeps working, so recovery is always possible; both the CLI and the MCP
  server require an explicit confirmation flag before sending it.
- **Control Center's noise-control tile.** It is fed by Apple's proprietary accessory protocol,
  which is why it appears for Apple/Beats headsets and not for the Edifier. Injecting a third-party
  tile into Control Center requires private APIs, disabling SIP and per-OS-version patching.
- **Codec or ANC takeover from a driver.** There is no Bluetooth-audio DriverKit family, and on
  Apple Silicon third-party kexts are not a usable route. A CoreAudio HAL plug-in in
  `/Library/Audio/Plug-Ins/HAL` can create virtual devices but cannot pick the A2DP codec or reach
  the headset's ANC.

That is precisely why this project exists in userspace: the menu bar app *is* the noise-control
surface, and `edifierctl` / `edifier-mcp` give scripts and coding agents the same control.

## The system-connected BLE link

macOS keeps a BLE link open to a paired headset (`EDIFIER BLE`, visible in
`system_profiler SPBluetoothDataType` as `Connected … Services: 0x400000 < BLE >`), and a connected
peripheral stops advertising. A scan therefore reports nothing even though the GATT service is up and
fully usable — measured on this machine: `edifierctl scan` (and a raw
`CBCentralManager` scan) listed 10-14 unrelated peripherals and never the headset, while
`retrieveConnectedPeripheralsWithServices:[48093801-…]` returned it immediately, with the GATT link
answering every command.

`edifier-link` therefore tries `system_ble::connect` (CoreBluetooth, on its own dispatch queue and a
dedicated owning thread, since the bindings make those objects `!Send`) before falling back to
`ble::connect` (btleplug scan). The menu bar app and the MCP server share that order, so a headset
that macOS already connected is found without advertising.
